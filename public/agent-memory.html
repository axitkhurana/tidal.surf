Agents Do Not Need More Memory. They Need Better State.

The useful question is not whether an agent has memory. It is what state crosses the boundary between two runs, and why the next run should trust it.

agent memory =
  write policy
+ store
+ retrieval policy
+ validation loop
!
The store is the least interesting term. Markdown, SQLite, vector search, graphs, mounted filesystems, and managed APIs can all work. The pipeline decides whether memory is useful.

01

First, Split The Word

Most memory discussions mix context, compaction, durable memory, and learning. They are different mechanisms with different failure modes.

MechanismWhat it meansExamplesCommon failure
ContextWhat the model sees nowprompt, files, tool outputtoo large or stale
CompactionWhat survives context pressuresession summarieslost intent
Durable memoryExternal state reused laterpreferences, repo rules, skillsstale authority
LearningChanged model or policyweights, fine-tuningusually not present
 
context pressure    = keep this run alive
session continuity  = keep this task coherent
durable memory      = change what a future run can know

Do not use long-term memory to solve context overflow. Use compaction for that. Durable memory starts when the harness decides state should cross a session boundary.

02

The Pipeline

A memory system is good only when a future action changes correctly, with source, scope, and deletion still intact.

StageDecisionBad default
CaptureWhat is a candidate?save everything
Extract/classifyWhat stable signal exists?flatten into notes
Scopeuser, repo, project, org, tool?global memory
Retrieve/injectwhat enters context now?top-k similarity
Validate/deleteis it true, and where must it disappear?trust old state
Memory enters context only through retrieval policy. Memory changes action only after validation policy.
03

Authority

A memory is not authoritative just because it is in context. Memory can suggest. Source of truth decides.

SourceAuthorityTreatment
Checked-in docs/code/configHighsource of truth
Cited current repo factHigh-mediumuse with citation/branch validation
Human-authored memoryMediuminstruction or hint
Generated memory with sourceMedium-lowvalidate before action
Generated memory without sourceLowhypothesis
Similar retrieved memoryHint onlyuse to search, not decide

File-first memory

Claude Code and Codex keep memory inspectable in local Markdown. Codex writes with async extraction/consolidation and reads cheaply: summary first, keyword search next. Inspectable, but paraphrases can miss.

Frozen prompt memory

Hermes freezes tiny `MEMORY.md` and `USER.md` snapshots at session start. Great for prompt stability. Risky when writes persist to disk but do not affect the current turn.

Managed memory

Anthropic memory stores mount under `/mnt/memory/` with access modes, immutable versions, optimistic concurrency, and redaction. Dreams consolidate into a separate output store for review.

Semantic and graph memory

Mem0, Zep, GBrain, and Letta optimize recall across sessions and tools. They improve discovery but add places for stale facts, leaked scopes, and failed deletion to hide.

RAG:          query -> top-k chunks -> answer
graph memory: query -> retrieve -> connect -> synthesize -> cite -> expose gaps
external memory output = claim + citation + freshness + missing information

System Details

The same pipeline shows up in different clothes. The useful comparison is not "who has memory"; it is what is always loaded, what is retrieved, how writes happen, and where governance breaks.

  -> separate output memory store

The input store is not mutated. Consolidation produces candidate state, not silent live-state edits.
06

The Contract

Start with the contract, not the database. `no_op` should be common. Most events should not become memory.

propose(event) -> candidate | null
write(candidate, scope, source) -> memory_id | no_op
retrieve(task, scope) -> ranked memories
validate(memory, task) -> trusted | stale | conflict | hint
inject(memory, mode) -> prompt text with source/authority
update(memory_id, source) -> new version
delete(memory_id) -> tombstone + derived cleanup
explain(memory_id) -> source, scope, versions, retrieval path
type: rule | fact | preference | episode | skill | hypothesis
scope: user | repo | project | org | tool
source: citation_or_event_id
content: "Deployments happen from main only after pnpm build passes."
confidence: high | medium | low
last_validated_at: timestamp
expires_at: timestamp | null
access: private | shared | read_only | read_write
valid_when: "task involves deploy/release/push"
contradicts: [...]

07

One Lifecycle

A memory is not the sentence the user said. It is the normalized state that survives with type, scope, source, validation path, and deletion behavior.

Raw Event

User: "Remember, this repo deploys from main only after pnpm build passes."

Bad Memory

User prefers pnpm build.

That bad memory turns a repo deployment rule into a vague user preference. The narrow policy should look more like this:

if task involves deploy/release/push:
  retrieve repo deployment rules
  validate against checked-in source
  cite before acting

09

Evaluation

Bad benchmark: did the agent remember the favorite color? Better benchmark: did yesterday's experience change today's decision correctly?

SessionTest
S1Teach a repo rule with source
S2Ask unrelated task; memory should not distract
S3Ask task where rule matters; memory should change action
S4Contradict/update rule
S5Ask again; current rule should win
S6Delete rule
S7Ask again; deleted rule should not resurface

Pass

Memory improves the relevant action and does not distract unrelated actions.

Update

New memory beats old memory when the source changes.

Delete

Deleted memory does not reappear through summaries, embeddings, or derived notes.

score =
  action correctness
+ citation validity
+ stale recall resistance
+ deletion correctness
+ false-positive rate
+ latency/token cost
+ cross-scope leakage tests

MemoryArena is useful because it couples memory with action. Stompy's coding-agent benchmark is useful because it reports a modest result: memory reduced exploration on harder tasks, did not materially improve code quality, and hurt trivial tasks. Memory helps when rediscovery is expensive.

11

Checklist

Before adding memory, answer these questions. If the answers are vague, the system has retrieval, not memory architecture.

#Question
1What memory types exist?
2Which events can create memory?
3Which writes require approval?
4What is always injected vs retrieved on demand?
5What is the source of authority?
6How are stale memories detected?
7How are contradictions represented?
8What is the delete path?
9What eval proves memory improves action?
10How can the operator inspect what loaded this turn?
11Do writes affect the current prompt or the next snapshot?
12Are memories scanned for prompt-injection or exfiltration before becoming prompt text?

The model is mostly stateless. The harness is becoming the runtime. Memory is the state layer of that runtime.
